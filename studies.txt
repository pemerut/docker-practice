Lesson 1

Kubernetes (K8s) - Container orchestration platform

Orchestration - Automated coordination and management of workloads

Cluster	- Set of machines managed together by Kubernetes

Node - Machine participating in a cluster

Control plane - Components that manage the cluster

Worker node	- Machine that runs application workloads

Pod	- Smallest deployable compute unit, containing one or more containers

Container runtime - Software that runs containers

Desired state - Configuration that Kubernetes should achieve

Actual state - Current observed condition of the cluster

Controller - Component that continuously works to reconcile state

Reconciliation - Correcting differences between desired and actual state

Replica - An instance of a workload, commonly represented by a Pod


Lesson 2.1

The Control plane

    kube-apiserver - Exposes the Kubernetes API
    etcd - Stores cluster state persistently
    kube-scheduler - Selects nodes for unscheduled Pods
    kube-controller-manager - Runs controllers that reconcile cluster state

The Worker node

    kubelet	- Ensures assigned Pods run on the node
    Container runtime - Creates and runs containers
    kube-proxy - Implements Service traffic forwarding rules

kube-apiserver — The central communication point
etcd — The cluster's persistent database
kube-scheduler — Choosing where Pods should run
kube-controller-manager — Maintaining the desired state

Examples of controllers

Deployment controller - Manages ReplicaSets for Deployments
ReplicaSet controller - Maintains the desired number of matching Pods
Node controller	- Monitors node health and handles relevant node lifecycle operations
Job controller - Manages Pods that perform tasks intended to complete
ServiceAccount controller - Manages aspects of ServiceAccount lifecycle


Lesson 2.1

kubelet — The node agent

The scheduler records the Pod's node assignment through the API server.
The kubelet on worker-2 observes the assigned Pod through the API.
The kubelet examines the Pod specification (PodSpec).
It coordinates container creation through the container runtime.
It monitors the containers and carries out applicable health probes.
It reports Pod and node status back through the API server.

Lesson 2.2

Container runtime

The runtime is responsible for operations such as preparing images, creating container execution environments, starting containers, and managing their lifecycle.

CRI stands for Container Runtime Interface.

CRI: Interface between Kubernetes' kubelet and a container runtime.
OCI: Open Container Initiative standards for container image formats and execution behavior.

Lesson 2.3

Pods have IP addresses and when they are replaced the address changes.
A Service provides a stable logical networking endpoint for accessing a set of Pods.

In common Linux configurations, kube-proxy observes Services and EndpointSlices through the Kubernetes API.

An EndpointSlice contains information about network endpoints, including eligible Pod addresses used by Services.
kube-proxy then configures the node's networking rules to implement Service traffic forwarding.

Lesson 2.5

Kubernetes components generally communicate changes to cluster state through the API server.

The Kubernetes API watch is a mechanism that allows clients to subscribe to a continuous stream of events for specific resources or collections, enabling real-time monitoring of changes without the inefficiency of polling.
Instead of repeatedly asking "did anything change?", the API server keeps an HTTP connection open and sends JSON-encoded events immediately when a resource is created, updated, or removed.

Lesson 2.6

kube-apiserver
    - API requests fail; cluster management is disrupted. Existing containers can continue running.
etcd (quorum lost)
    - Persistent cluster changes cannot normally be committed; API operations and reconciliation are affected.
kube-scheduler
    - Newly created, unscheduled Pods cannot normally receive automatic node assignments. Existing assigned Pods can continue.
kube-controller-manager
    - Controllers stop reconciling; missing Pods may not be replaced by their controllers, and other controller-managed operations stall.
kubelet
    - The node loses its Kubernetes execution agent; its containers might continue running temporarily, but management and status reporting are disrupted.
Container runtime
    - Starting or managing containers fails; effects on already-running containers depend on runtime failure details.
kube-proxy
    - Service routing rules may stop updating. Existing rules might continue working, depending on the implementation.
CNI networking implementation
    - Pod network creation or connectivity can fail, depending on the type of failure.
CoreDNS
    - DNS lookups inside the cluster may fail while some direct IP connectivity remains functional.


Lesson 2.7

Static Pods in Kubernetes are workloads managed directly by the kubelet daemon on a specific node, bypassing the Kubernetes API server and scheduler for creation and lifecycle management. 
Unlike standard pods, they are defined by YAML or JSON manifest files placed in a designated directory or served via a web URL, which the kubelet continuously monitors to start, restart, or delete pods. 

The primary use case for static pods is bootstrapping and maintaining critical control plane components such as the kube-apiserver, etcd, kube-scheduler, and kube-controller-manager.

Lesson 3

A Kubernetes Deployment is a resource object that provides declarative updates to applications, allowing users to describe an application’s life cycle, including which container images to use, the desired number of pods, and how updates should be applied. 
It is primarily designed for managing stateless applications, ensuring that a specified number of pod replicas remain running and healthy by automatically replacing failed instances and managing rolling updates or rollbacks to minimize downtime. 

A Kubernetes Service is an API object that provides a stable network endpoint and DNS name for a logical group of Pods, abstracting away their ephemeral IP addresses.
It enables reliable service discovery and built-in load balancing by routing traffic from the Service’s static virtual IP (ClusterIP) to healthy, matching Pods based on label selectors.
