1.1 What exactly is scheduling?

Scheduling is the process of selecting a suitable node for a Pod that hasn't yet been assigned to one.

The scheduler doesn't start containers.
Its responsibility is to determine which node should run a Pod.


1.2 The two primary scheduling stages

The scheduler evaluates candidate nodes using two main stages.

Filtering: Eliminate nodes that cannot satisfy the Pod's requirements.
Scoring: Rank the remaining eligible nodes and select a suitable candidate.

Besides insufficient resources, a node might be ineligible because of:
- A restrictive node selector.
- Required node affinity.
- An untolerated taint.
- Storage or volume placement constraints.
- Pod affinity or anti-affinity requirements.
- Node availability or other scheduling restrictions.


2.0 CPU and memory requests

Kubernetes needs to understand how many resources an application requires.

resources:
  requests:
    cpu: "250m"
    memory: "256Mi"


2.1 CPU units

Kubernetes commonly expresses CPU resources in cores or millicores.

cpu: "250m"  -  requesting 0.25 CPU
It doesn't mean the Pod receives exclusive ownership of 25% of a physical processor.


2.2 Memory units

Kubernetes supports binary memory units such as:

Ki	1,024 bytes
Mi	1,048,576 bytes
Gi	1,073,741,824 bytes


2.3 resource request

A request tells Kubernetes the amount of a resource to account for when placing a Pod and allocating its resource share.

Schedule this Pod onto a node that has sufficient allocatable CPU and memory capacity
ccounting for resources already requested by other Pods.

The Pod might remain Pending with an Insufficient cpu scheduling event.


3.0 Resource limits

Requests and limits solve different problems.
A request affects scheduling and resource allocation.
A limit controls how much of a resource the container is allowed to consume.

resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"


3.1 CPU limits

The CPU limit is 1000m, equivalent to one CPU core of processing capacity.
The container may use CPU above its request when CPU time is available, but the configured limit caps its CPU usage.

When the container tries to exceed the CPU limit, Linux can throttle it.


3.2 Memory limits

The application experiences a memory leak and attempts to use more memory than its cgroup limit allows.
The kernel may terminate a process using its Out-of-Memory (OOM) mechanism.

Kubernetes could subsequently report:
Last State: Terminated
Reason:     OOMKilled
Exit Code:  137

A memory limit breach can result in termination, unlike ordinary CPU throttling.
