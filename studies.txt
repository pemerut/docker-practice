lesson 1.1

A Pod can contain:
1. One or more application containers.
2. Shared networking resources.
3. Shared storage volumes.
4. Configuration governing how the containers execute.


lesson 2.1

Containers inside the same Pod share a network namespace.

This means they share:
- A Pod IP address.
- Network interfaces.
- The same TCP/UDP port space.

Containers within the same Pod can communicate through localhost.
Containers in different Pods normally communicate using Pod IP addresses or Services.

lesson 3.0

Kubernetes tracks the Pod's overall condition through its status fields.

status:
  phase: Running

The Pod phase represents a high-level summary of its lifecycle.


lesson 3.1

There are five possible Pod phases.

Pending - Kubernetes accepted the Pod, but its containers haven't finished preparation for execution
Running - The Pod is assigned to a node, its containers have been created, and at least one is running or starting/restarting
Succeeded - All relevant containers completed successfully and won't restart
Failed - All relevant containers terminated, and at least one failed
Unknown - Kubernetes cannot determine the Pod's current state


lesson 4.0

A Pod has a lifecycle phase.
Each container inside that Pod has its own state.

Waiting	- The container isn't currently running and is waiting to start or restart
Running	- The container process is executing
Terminated - The container process has finished execution


lesson 5

You want Kubernetes to know when the application is ready to serve HTTP requests.
readinessProbe:
  httpGet:
    path: /health
    port: 8080

  initialDelaySeconds: 2
  periodSeconds: 5

This tells the kubelet to periodically make an HTTP request to your application's /health endpoint.
If the probe succeeds, the container can be considered ready.
If it fails, the Pod may become NotReady.

Readiness - Pod becomes unready for Service traffic
Liveness - Container restart
Startup - Continued startup checks, followed by restart if the failure threshold is reached


lesson 7

A ReplicaSet is a Kubernetes workload resource that maintains a desired number of matching Pod replicas.
Without a higher-level workload controller, Kubernetes won't automatically recreate an arbitrary standalone Pod just because it was deleted.

spec:
  replicas: 3

- The ReplicaSet controller continuously works to maintain three matching Pod objects.

- ReplicaSet controller creates or deletes Pod objects.
- Scheduler assigns unscheduled Pods to nodes.
- Kubelet coordinates their execution.
- Container runtime runs their containers.
The ReplicaSet is concerned with maintaining the desired number of Pods.


lesson 8

A Deployment is a higher-level Kubernetes workload resource that manages ReplicaSets and provides declarative application updates.

Deployments provide these higher-level capabilities.
1. Introduce the new application version.
2. Manage the transition from old Pods to new Pods.
3. Maintain application availability where possible.
4. Track rollout revisions.
5. Roll back if the new version fails.

During a rolling update, a Deployment may temporarily manage both old and new ReplicaSets.


lesson 10

RollingUpdate - Rather than terminating every existing Pod immediately, Kubernetes gradually introduces new Pods while removing old ones.
The objective is to maintain application availability while introducing the new version.

maxSurge
This controls how many extra Pods Kubernetes can create above the desired replica count during a rolling update.

maxUnavailable
This controls the maximum number of desired replicas that may be unavailable during the rollout.

replicas: 4

strategy:
  type: RollingUpdate

  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 1

Recreate - With Recreate, Kubernetes terminates the old application Pods before creating the new ones.
This strategy can cause downtime.

However, it may be appropriate when application versions cannot safely coexist.
