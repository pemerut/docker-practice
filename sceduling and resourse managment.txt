1.1 What exactly is scheduling?

Scheduling is the process of selecting a suitable node for a Pod that hasn't yet been assigned to one.

The scheduler doesn't start containers.
Its responsibility is to determine which node should run a Pod.


1.2 The two primary scheduling stages

The scheduler evaluates candidate nodes using two main stages.

Filtering: Eliminate nodes that cannot satisfy the Pod's requirements.
Scoring: Rank the remaining eligible nodes and select a suitable candidate.

Besides insufficient resources, a node might be ineligible because of:
- A restrictive node selector.
- Required node affinity.
- An untolerated taint.
- Storage or volume placement constraints.
- Pod affinity or anti-affinity requirements.
- Node availability or other scheduling restrictions.


2.0 CPU and memory requests

Kubernetes needs to understand how many resources an application requires.

resources:
  requests:
    cpu: "250m"
    memory: "256Mi"


2.1 CPU units

Kubernetes commonly expresses CPU resources in cores or millicores.

cpu: "250m"  -  requesting 0.25 CPU
It doesn't mean the Pod receives exclusive ownership of 25% of a physical processor.


2.2 Memory units

Kubernetes supports binary memory units such as:

Ki	1,024 bytes
Mi	1,048,576 bytes
Gi	1,073,741,824 bytes


2.3 resource request

A request tells Kubernetes the amount of a resource to account for when placing a Pod and allocating its resource share.

Schedule this Pod onto a node that has sufficient allocatable CPU and memory capacity
ccounting for resources already requested by other Pods.

The Pod might remain Pending with an Insufficient cpu scheduling event.


3.0 Resource limits

Requests and limits solve different problems.
A request affects scheduling and resource allocation.
A limit controls how much of a resource the container is allowed to consume.

resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"


3.1 CPU limits

The CPU limit is 1000m, equivalent to one CPU core of processing capacity.
The container may use CPU above its request when CPU time is available, but the configured limit caps its CPU usage.

When the container tries to exceed the CPU limit, Linux can throttle it.


3.2 Memory limits

The application experiences a memory leak and attempts to use more memory than its cgroup limit allows.
The kernel may terminate a process using its Out-of-Memory (OOM) mechanism.

Kubernetes could subsequently report:
Last State: Terminated
Reason:     OOMKilled
Exit Code:  137

A memory limit breach can result in termination, unlike ordinary CPU throttling.


4.1 Capacity versus allocatable

Kubernetes distinguishes between:

Capacity: The total amount of a resource reported for a node.

Allocatable: The amount of that resource made available for Pods after accounting for certain system and eviction reservations.

Overcommitment means allowing workloads to collectively have access to more potential resource consumption than the machine can physically provide simultaneously.


5.1 - Node labels

Nodes can have labels, just like Pods.

disktype: ssd
environment: production

Kubernetes can use these labels as part of node selection.


5.2 nodeSelector

spec:
  nodeSelector:
    disktype: ssd

This creates a mandatory requirement.
The scheduler can consider only nodes with the matching label.

If no node matches, the Pod can remain Pending.

A node selector doesn't override CPU requirements or taints.
The selected node must satisfy the other mandatory constraints too.


5.3 Node affinity

Node affinity provides more expressive scheduling rules.

requiredDuringSchedulingIgnoredDuringExecution - Hard requirement when scheduling
preferredDuringSchedulingIgnoredDuringExecution - Soft preference when scheduling

RequiredDuringScheduling
The scheduler must satisfy the rule to place the Pod.

PreferredDuringScheduling
The scheduler tries to satisfy the preference but may choose another suitable node.


5.4 Pod affinity and anti-affinity

Node affinity looks at node labels.
Pod affinity and anti-affinity look at other Pods.

For example:
- Pod affinity: Prefer running a frontend near a related backend.
- Pod anti-affinity: Avoid placing all three Go API replicas on the same node.


6.1 - Taints

A taint is applied to a Node.

kubectl taint nodes gpu-worker dedicated=gpu:NoSchedule

Key - dedicated
Value - gpu
Effect - NoSchedule


6.2 What is a toleration?

A toleration is applied to a Pod.
It tells the scheduler that the Pod can tolerate a matching node taint.

tolerations:
  - key: dedicated
    operator: Equal
    value: gpu
    effect: NoSchedule

A toleration does not force a Pod onto a node.
It merely prevents the matching taint from excluding that Pod.


6.3 The three taint effects

NoSchedule	Blocks newly scheduled Pods without a matching toleration
PreferNoSchedule	Soft scheduling restriction; scheduler tries to avoid the node
NoExecute	Can prevent scheduling and evict existing Pods that don't tolerate the taint

When a node becomes NotReady or unreachable, Kubernetes can apply condition-based taints.
Relevant controllers may then evict affected Pods according to configured tolerations and timing.
This connects scheduling policies to cluster self-healing.


7 — Quality of Service (QoS)

Kubernetes assigns Pods a Quality of Service class based on their resource configuration.

The traditional three QoS classes are:
- Guaranteed
- Burstable
- BestEffort

hese classifications matter particularly when a node experiences resource pressure.


7.1 Guaranteed

A Pod receives Guaranteed QoS when all its containers have CPU and memory requests and limits
with the request equal to the limit for each resource.

resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"

The Pod qualifies for Guaranteed QoS.
That doesn't mean it can never fail or be evicted.


7.2 Burstable

A Pod is Burstable when it has some relevant resource configuration but doesn't qualify for Guaranteed.

resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"

It's allowed to consume above its requests up to the applicable limits.


7.3 BestEffort

A Pod is BestEffort when its containers have no CPU or memory requests or limits.

Under resource pressure, they may be more vulnerable to eviction.
BestEffort is always evicted first, followed by Burstable, followed by Guaranteed.
