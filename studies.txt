lesson 1.1

Container-to-container within a Pod	A logging sidecar contacts the Go server using localhost
Pod-to-Pod	Go API Pod contacts a PostgreSQL Pod
Pod-to-Service	Client contacts go-api using a stable DNS name
External-to-Service	A browser accesses your application from the internet

The most important foundational rule is that every ordinary Pod has its own IP address,
and Pods should be able to communicate over the cluster network without requiring
the application to know which physical node hosts the destination.

lesson 3.1

CNI stands for Container Network Interface.

It defines an interface through which container runtimes and network plugins coordinate container networking.

Configure Pod network interfaces.
Assign Pod IP addresses.
Configure routes.
Connect Pods running on different nodes.
Implement network policies.
Use overlays, native routing, eBPF, or other networking techniques.


lesson 4.1

A Pod can disappear and be replaced by a new Pod with a different IP address.
If clients connect directly to those addresses, they must somehow discover replacements whenever the Pod population changes.

A Service provides a stable networking abstraction over a set of backends.

lesson 4.2

Service indentify pods by labels and selectors

apiVersion: v1
kind: Service
metadata:
  name: go-api
spec:
  type: ClusterIP
  selector:
    app: go-api
  ports:
    - port: 80
      targetPort: 8080


lesson 4.3

An EndpointSlice is a Kubernetes API resource describing a set of network endpoints used by Services.
For a normal Service with a selector, the EndpointSlice controller maintains information about matching Pods.

Pod IP addresses.
Ports.
Endpoint readiness conditions.
Node and zone information.

A Service doesn't directly contain all of its backend Pod IPs.
EndpointSlices provide the scalable endpoint representation.
