1.1 Pods are ephemeral

A Kubernetes controller creates a replacement Pod with a new container.

Application lifecycle and data lifecycle should be independent
when data must survive workload replacement.


1.2 Storage during different kinds of failures

A PersistentVolume does not guarantee that data can always move between nodes.
A local disk, for example, is tied to a particular machine.

It also doesn't replace database backups.
persistent storage can outlive the Pod using it


2.1 Volumes versus volume mounts

A Pod's volumes field describes the storage source.

A container's volumeMounts field describes where that storage appears inside the container.

apiVersion: v1
kind: Pod
metadata:
  name: example
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
      volumeMounts:
        - name: shared-data
          mountPath: /app/data

  volumes:
    - name: shared-data
      emptyDir: {}

The name connects the volume definition to the container's mount.
The mountPath tells Kubernetes where to make the storage available inside that container.


2.2 What is emptyDir

An emptyDir is a temporary volume associated with a Pod.
Kubernetes creates it when the Pod is assigned to a node and the storage is prepared.
It initially contains no files. The volume can be shared by multiple containers in the same Pod.

could use it for:
- Temporary files.
- A shared cache.
- Files exchanged between application and sidecar containers.
- Intermediate processing data.

An emptyDir generally survives individual container restarts while the Pod continues to exist on the node.
emptyDir is ephemeral storage, not persistent storage.


2.3 What is hostPath

A hostPath volume mounts a file or directory from the worker node's filesystem into a Pod.

volumes:
  - name: host-data
    hostPath:
      path: /srv/application-data
      type: Directory

This connects the Pod to a specific path on its node.

Suppose the Pod originally runs on Worker 1 and is replaced on Worker 2.
The replacement Pod would use /srv/application-data on Worker 2,
which is not automatically the same data as on Worker 1.

Furthermore, hostPath can expose sensitive host files to containers and introduces security risks.


3.0 PersistentVolumes and PersistentVolumeClaims

- abstractions that separate an application's storage requirements from the underlying storage infrastructure.

he three most important objects are:
- PersistentVolume (PV)
- PersistentVolumeClaim (PVC)
- StorageClass


3.1 PersistentVolume (PV)

A PersistentVolume is a cluster-scoped Kubernetes API resource representing a provisioned piece of storage.

For example, a PV may represent storage backed by:
- A cloud block storage volume.
- An NFS-based storage system.
- A CSI-managed storage system.
- A local persistent disk.

The PersistentVolume object describes storage properties, including capacity, access modes, and storage-specific details.
It's a Kubernetes resource representing that storage.


3.2 PersistentVolumeClaim (PVC)

A PersistentVolumeClaim is a request for storage made by a workload or user.

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi

The PVC doesn't normally care whether the capacity comes from AWS EBS, a network storage appliance,
or another compatible backend.


3.3 PV versus PVC: The relationship

Pod → PVC → PV → Storage backend
A PVC is namespaced, while a PV is cluster-scoped.

This design separates the application consuming storage from the administrator or system providing it.


3.4 What does Bound mean

When Kubernetes successfully associates a PVC with a suitable PV, the claim enters the Bound phase.

A PVC may also remain Pending while waiting for an appropriate PV or dynamic provisioning.


4.1 Static versus dynamic provisioning

Static - An administrator provisions storage and creates a PV. A compatible PVC can bind to it.
Dynamic - A PVC requests a StorageClass, and a provisioner creates suitable storage automatically.

A StorageClass defines a category of storage and the mechanism used to provision it.
The classes could represent different storage backends or performance characteristics.

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
spec:
  storageClassName: fast-storage
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi


4.2 The important StorageClass fields

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-storage
provisioner: csi.example.com
reclaimPolicy: Retain
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true

The provisioner name is illustrative. It would need to reference a real installed storage driver.

provisioner - The storage provisioner responsible for creating volumes
reclaimPolicy - What should happen when a dynamically provisioned volume is released
volumeBindingMode - When volume provisioning and binding occur
allowVolumeExpansion - Whether the class supports requested expansion of existing volumes


4.3 Immediate versus WaitForFirstConsumer

Immediate: Provisioning and binding happen when the PVC is created,
without waiting for a consuming Pod's scheduling constraints.

WaitForFirstConsumer: Provisioning or binding is delayed until a Pod consuming the PVC participates in scheduling,
allowing topology constraints to be considered.

For topology-constrained storage, WaitForFirstConsumer can help avoid volumes being created in unsuitable locations.


5.0 Access modes

Some volumes can be attached to only one node for writing. Others support access from multiple nodes.

ReadWriteOnce (RWO)	- Read-write access by one node
ReadOnlyMany (ROX) - Read-only access from multiple nodes
ReadWriteMany (RWX) - Read-write access from multiple nodes
ReadWriteOncePod (RWOP) - Read-write use restricted to a single Pod, with supported CSI storage

A ReadWriteOnce volume may be used by multiple Pods running on the same node, where the storage backend supports that arrangement.


6.0 CSI

CRI: Container Runtime Interface
CNI: Container Network Interface

CSI — Container Storage Interface.
CSI is the standard interface used to integrate storage systems with container orchestration platforms.


6.1 What does CSI do

Depending on the driver and backend, CSI integration can coordinate operations such as:
- Creating and deleting volumes.
- Attaching volumes to nodes.
- Preparing and mounting volumes.
- Expanding volumes.
- Creating storage snapshots when supported.


6.2 PVC Bound does not guarantee a successful mount

PVC: Bound
Pod: ContainerCreating

Possible reasons include:
- The volume cannot attach to the selected node.
- Storage topology is incompatible.
- A CSI driver is unhealthy.
- Mounting fails.
- Another node is using a volume that doesn't support the requested concurrent attachment.


7.0 — Reclaim policies and data deletion

Normally, deleting a Pod doesn't automatically delete its PVC.
But what if the PVC itself is deleted?
That is where the PersistentVolume's reclaim policy matters.

There are two current main reclaim policies.


7.1 Delete

persistentVolumeReclaimPolicy: Delete

When the associated claim is deleted and the storage is released, Kubernetes and the provisioner
normally arrange to delete the PV and underlying storage asset.

This can permanently destroy data.


7.2 Retain

persistentVolumeReclaimPolicy: Retain

Kubernetes preserves the underlying storage asset after the claim is deleted.
An administrator must then handle recovery, cleanup, or reuse.


8.1 Stateless versus stateful

Stateful describes systems, applications, or protocols that retain memory of previous interactions and maintain context between requests.
stateless describes a system, protocol, or application that does not retain information about past interactions or user sessions. 


8.2 What is a StatefulSet

A StatefulSet is a Kubernetes workload resource designed for applications that need stable Pod identity and, commonly, stable storage.

Pods have stable ordinal identities
Commonly used for stateful applications
Pod names follow stable ordinals, such as postgres-0
Supports per-Pod PVCs through volumeClaimTemplates
Supports ordered identity-aware deployment and update behavior

Each Pod can have its own persistent storage claim.
When postgres-0 is replaced, the new Pod can use the existing claim associated with that identity.


9.1 ConfigMap

A ConfigMap is an API object containing non-sensitive key-value configuration data.

apiVersion: v1
kind: ConfigMap
metadata:
  name: go-api-config
data:
  APP_ENV: "production"
  LOG_LEVEL: "info"
  HTTP_PORT: "8080"
  DB_HOST: "postgres.default.svc.cluster.local"


9.2 Environment-variable injection

A Deployment can reference a ConfigMap:

env:
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef:
        name: go-api-config
        key: LOG_LEVEL


The container then receives: LOG_LEVEL=info


9.3 What happens if a ConfigMap changes

Environment variables: Normally remain unchanged inside a running container.
The Pod must be recreated to receive updated values.

Mounted ConfigMap files: Kubernetes can eventually update the mounted files automatically, but the application may need to reload them.
Mounts using subPath don't receive the usual automatic updates.


10.0 Secrets

Kubernetes provides Secrets for sensitive information.

Common examples include:
- Database passwords.
- API tokens.
- TLS certificates and private keys.
- Registry credentials.

10.1 Secret fields

apiVersion: v1
kind: Secret
metadata:
  name: postgres-credentials
type: Opaque
stringData:
  password: "example-only-password"

An application can reference the Secret similarly to a ConfigMap:

env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: postgres-credentials
        key: password
